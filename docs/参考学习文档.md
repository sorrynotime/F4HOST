# 多款手柄兼容：芯片能力与参考学习文档

[返回文档目录](README.md)

调研日期：2026-11-26。

> 说明：芯片参数来自 ST 官方页面，当前工程占用来自仓库中的 `F4HOST.map`；GitHub 项目的信息来自各仓库页面/README，未逐行审计其源码。下文把“已核实”和“需实测确认”分开写，避免把推测当结论。

## 1. 结论先行

1. **不是芯片整体内存不够，而是“按设备描述写死的容量”不够。** STM32F401RC 有 256 KB Flash、64 KB SRAM、84 MHz Cortex-M4F，当前 Keil 构建只用了约 41 KB RO 和 10.6 KB RW+ZI，总预算很宽裕。但协议栈把每设备的配置描述符、接口/端点数、HID 报告描述符和字段表都写成了固定小容量；不同设备描述结构不同，很容易超出这些上限。多数超限路径会被代码转成失败码而不是写爆内存，真正让现象变成“死机”的，是失败之后没有超时、没有 Pipe 回收、`HOST_ABORT_STATE` 无法恢复。
2. **兼容“大部分手柄”要分层看：**
   - 标准 HID 手柄 / 接收器的 PC 模式：有条件做到广覆盖，靠报告描述符解析 + 统一状态映射。
   - 厂商协议手柄（Xbox、PS、Switch 等）：需要按家族写专用驱动；部分还要求初始化握手、认证或加密，不能靠通用 HID 解析器解决。
   - 蓝牙手柄直连：本芯片没有蓝牙，需要外接 BT dongle + BTHID，不属于当前硬件范围。
   - 多手柄同时接入：芯片只有一个 USB FS 根口，必须外挂 Hub，且协议栈要有 Hub 类和多设备实例；当前 ST Host 框架不支持。
3. **建议顺序：先“不死机”，再“广兼容”，最后“多设备”。** 把 P0 的超时、Pipe、ABORT 状态问题修掉，收益远大于直接堆新手柄协议。

## 2. 芯片能力盘点

| 项目 | 官方/实测数据 | 对本项目的意义 |
| --- | --- | --- |
| 内核 | Arm Cortex-M4F，84 MHz，DSP + 单精度 FPU，105 DMIPS / 285 CoreMark | 报告描述符解析、按包解码都属于轻量计算，算力有富余 |
| Flash | 256 KB | 当前 `F4HOST.map` 的 `Total RO Size` 为 41,956 B（约 41 KB），还有大量空间放多套手柄解析表和兼容逻辑 |
| SRAM | 64 KB | 当前 `Total RW Size` 为 10,632 B（约 10.4 KB）；`docs/05-build-and-validation.md` 记录脚本构建 RW+ZI 约 12.9 KB。需再预留栈/堆，但仍有充足预算 |
| USB | USB 2.0 FS OTG，可做 Host，12 Mbit/s | 单根口；多设备必须靠 Hub。按 1 ms 轮询、每设备 64 B 输入估算，4 个手柄约 256 KB/s，带宽不是瓶颈 |
| 调试资源 | USART2 诊断已接通 | 适合输出状态机轨迹、描述符和失败码 |

结论：在 F401RC 上做“多个标准 HID 手柄 + 若干厂商接收器白名单”是现实的；做“所有主流手柄全功能兼容（含蓝牙、震动、认证）”不现实，范围需要明确收窄。

## 3. 当前工程“换一款手柄就死机”的代码层原因

以下行号以当前提交为准。**已确认的结构性缺陷**和**需实测确认的疑点**分开列出。

### 3.1 已确认的结构性缺陷

| 优先级 | 位置 | 现象与证据 |
| --- | --- | --- |
| 高 | `Msp/Middlewares/ST/STM32_USB_Host_Library/Core/Src/usbh_ctlreq.c:879,949,1010,1070` | `Control.timer` 只被赋值，全文件没有任何超时比较。`CTRL_DATA_IN_WAIT` 遇到 `URB_NOTREADY`/`URB_IDLE` 时状态保持 `USBH_BUSY`，控制传输可永久卡住 |
| 高 | `Lib/host_gamepad/host_gamepad.c:125-161` | `requests()` 发 `0x2200` GET_DESCRIPTOR，收到 `USBH_BUSY` 就直接返回；新手柄若对该接口 NAK，`usbh_core.c:718-736` 会永远停在 `HOST_CLASS_REQUEST` |
| 高 | `Msp/USB_HOST/Target/usbh_conf.c:361-368` | `USBH_LL_ClosePipe()` 是空函数，不调用 `HAL_HCD_HC_Halt()`。Pipe 复用时旧 URB 状态、data toggle、`xfer_buff` 残留 |
| 高 | `Msp/Middlewares/ST/STM32_USB_Host_Library/Core/Src/usbh_core.c:793-795` | `HOST_ABORT_STATE` 是死状态，没有恢复路径，只能靠拔插；进入时也不调用类的 `DeInit`，Pipe 不释放 |
| 高 | `Msp/Middlewares/ST/STM32_USB_Host_Library/Core/Src/usbh_core.c:706-710,728-732` | 无匹配类、类 `Requests()` 返回 FAIL 都会进 ABORT。`host_gamepad.c:74` 又跳过所有 Boot HID 接口，只有 Boot HID 的手柄更容易直接命中 |
| 中 | `Msp/Middlewares/ST/STM32_USB_Host_Library/Core/Src/usbh_core.c:749-755` | `HOST_CLASS` 直接调用 `BgndProcess()` 并忽略返回值；类一旦返回 FAIL 就永久早退（`host_gamepad.c:166`） |
| 高 | `Msp/USB_HOST/Target/usbh_conf.h:66-84` | 容量写死：每设备 4 端点、8 接口、配置描述符 512 B、2 个类，数据缓冲 1024 B。复合手柄超出上限即识别失败，详见 3.2 |
| 中 | `Lib/host_gamepad/gamepad_hid.c:21-124` 与 `host_gamepad.c:158` | HID 解析器对 Long item、Delimiter、Usage 数量、多 Report ID 等都有硬失败分支；失败后 `layout` 清空，但 `usb_ready` 仍被置 1，表现为“插上没反应” |
| 中 | `Lib/host_gamepad/gamepad_app.c:25-36,45-63` | `hex_line()` 中 `count = length - dump_pos` 没有下溢保护；描述符长度在转储过程中变小时可能越界读取，进而触发 HardFault |
| 中 | `Msp/Middlewares/ST/STM32_USB_Host_Library/Core/Src/usbh_core.c:757-791` 与 `1206-1216` | 快速换插时若新设备在断开事件被处理前完成连接，会跳过 `HOST_DEV_DISCONNECTED`，旧类、Pipe 和状态不清零 |

### 3.2 固定容量与设备描述差异（换设备最直接的触发点）

不同手柄/接收器的描述符结构差异很大：接口数、每接口端点数、配置描述符总长、HID 报告描述符长度和字段数量都不一样。当前工程把这些容量写死，因此“换一款设备”本质上会直接撞上这组写死的假设。

| 固定容量 | 代码位置 | 设备超出后会怎样 |
| --- | --- | --- |
| 配置描述符 512 B | `Msp/USB_HOST/Target/usbh_conf.h:78`；`usbh_ctlreq.c:456` | `wTotalLength` 被 `MIN(..., 512)` 截断，设备真实描述符更长时**静默只取前 512 B**，后面的接口/端点根本看不到 |
| 每设备 8 接口、4 端点 | `Msp/USB_HOST/Target/usbh_conf.h:66,69`；`usbh_ctlreq.c:468,485,527` | 超出部分被解析循环忽略；如果手柄接口排在后面，就找不到匹配接口 → 无匹配类 → ABORT |
| 报告描述符 1024 B | `Lib/host_gamepad/host_gamepad.h:13`；`host_gamepad.c:100-104` | 大于 1024 B 时直接置 `descriptor_length=0`、`descriptor_status=-1`；但 `requests()` 仍在 158 行置 `usb_ready=1`，表现“插上没数据” |
| 最多 8 个 Report ID、64 个字段 | `Lib/host_gamepad/gamepad_hid.h:6-7`；`gamepad_hid.c:82-88,102-106` | 复杂描述符触发硬失败，`GP_ParseDescriptor()` 返回 −1，字段表清空 |
| 输入包 64 B、端点 MPS ≤ 64 B | `Lib/host_gamepad/gamepad_hid.h:8`；`host_gamepad.c:77-80` | MPS 大于 64 或没有 Interrupt IN 的接口被直接跳过，设备等于不存在 |
| 单一全局 `g_gamepad` | `Lib/host_gamepad/host_gamepad.h:31` | 只能保存一个设备上下文；换设备必须完整拔插重建，放大清理不彻底的问题 |

需要强调区别：**这些上限大多不会造成缓冲区溢出**——`gamepad_hid.c` 对字段数、Report ID 和位宽都有边界检查，`USBH_Get_CfgDesc()` 也检查长度大于缓冲时返回 `NOT_SUPPORTED`。它们的实际后果是“设备解析失败/被忽略/描述符被截断”，再叠加 3.1 的超时缺失、ABORT 死状态和 Pipe 不回收，才表现为换一个插上就卡死。

所以修复方向不是简单把数组改大：一是把容量做成可配置并按设备留余量，二是任何超限都必须走可观测、可恢复的失败路径。

### 3.3 需实测确认的疑点

- `usbh_conf.c:205` 关闭 SOF，而 `USBH_LL_IncTimer()` 只在 `HAL_HCD_SOF_Callback`（`usbh_conf.c:124-127`）里调用；`host_gamepad.c:226` 的轮询周期和 `212` 的 1 秒超时都依赖 `host->Timer`。需确认 HAL 在 SOF 关闭时是否仍回调。
- `usbh_conf.c:538-541` 的 `USBH_Delay()` 使用 `HAL_Delay()`，加上 VBUS 相关的 200 ms 延时，插拔时会阻塞主循环，放大“卡死”感受。
- `Msp/Core/Src/main.c:180-189` 的 `Error_Handler()` 是关中断死循环，异常后没有任何串口线索。

### 3.4 定位实验建议

1. 换手柄后打印 `host->gState` 和 `host->Control.state`：若停在 `HOST_CLASS_REQUEST`/`CTRL_DATA_IN_WAIT`，对应 3.1 第 1、2 条。
2. 打印 `GP_ParseDescriptor()` 返回值和 `g_gamepad.descriptor_status`：失败但 `usb_ready=1` 对应第 8 条。
3. 打印 `CfgDesc.wTotalLength`、`bNumInterfaces`、各接口 `bNumEndpoints`、`descriptor_length`、`layout.report_count`、`layout.field_count`，与 3.2 的上限逐项对照，确认是哪一项被卡住。
4. 调试器观察 `HAL_HCD_HC_Halt()` 是否从未被调用、`hhcd.hc[n].xfer_buff` 是否残留旧地址：对应 3.1 第 3 条。
5. 若进入 `HOST_ABORT_STATE`，核对是“无匹配类”还是“Requests FAIL”，再决定是否要放宽接口选择或补超时。

## 5. 提炼出来的工程做法

### 5.1 架构分层

```text
USB Host Core（枚举、控制/中断传输、Pipe）
  └─ 设备匹配层（VID/PID + class/subclass/protocol + 接口特征 + quirk 表）
       ├─ 通用 HID 驱动（报告描述符 → 字段映射 → 统一状态）
       └─ 厂商驱动（初始化/握手 + 专用报告解析）
            └─ 统一 Gamepad 状态与事件（Connect/Disconnect/Report/Error）
```

关键原则：**传输层不解析语义，解析层不碰 Pipe，应用层不猜偏移。**

### 5.2 必须补的可靠性机制

1. 所有控制传输加超时（建议 100–500 ms）和有限次数重试（2–3 次），失败后走统一恢复流程。
2. 恢复流程固定为：类 `DeInit()` → `HAL_HCD_HC_Halt()` → `USBH_ClosePipe()` → `USBH_FreePipe()` → 清空该类上下文 → 等待重新插拔；不要留 `HOST_ABORT_STATE` 死状态。
3. `BgndProcess()` 的返回值必须被核心层处理，FAIL 要触发恢复而不是无限调用。
4. 设备上下文从“一个全局 `g_gamepad`”改为按设备/接口分配（静态池），包含 pipe、toggle、report layout、状态、超时计数。
5. 把配置描述符、接口/端点数、报告描述符和字段表的上限改为可配置，按最坏设备留余量；`wTotalLength` 被截断时必须报明确失败码，不能静默当成功。
6. 描述符与报告解析全部走边界检查；非法包直接丢弃并计数，不产生半更新状态。
7. 断连和报告超时都要清掉旧按键/摇杆状态，避免“按键卡住”。
8. 修掉 `gamepad_app.c` 的转储下溢；保留 RAW 和失败码日志，作为兼容新设备的证据。

### 5.3 兼容扩展路线

| 阶段 | 目标 | 验收标准 |
| --- | --- | --- |
| P0 | 不死机 | 连续换插 5+ 款设备不进死状态；所有失败都有日志和明确恢复路径 |
| P1 | 通用 HID 广覆盖 | 多款 PC 模式手柄/接收器能读出按钮、轴、方向帽；不靠固定偏移 |
| P2 | 厂商白名单 | 按 VID/PID + 接口特征接入 2–3 个常见接收器家族，初始化序列可配置 |
| P3 | Hub 与多设备 | 静态池支持 N 个设备轮询，单设备异常不影响其他设备 |
| P4 | 扩展能力 | 蓝牙 dongle、震动/灯光、校准/死区等；按需求裁剪，不盲目追求 |

### 5.4 测试矩阵建议

每新增一款设备至少记录：型号/固件、VID/PID、接口与端点、配置描述符长度、HID 报告描述符、RAW 样本、按键/轴映射证据、插拔/失联/重连结果、失败时的 `gState` 与错误码。沿用 `docs/04-bringup.md` 的日志规范。

## 6. 范围判断

“兼容大部分手柄”在这个芯片上可以作为一个渐进目标，但建议把成功定义为：

- 插入任何设备都不会死机，不支持的设备能明确报出原因；
- 标准 HID 手柄覆盖尽可能多；
- 厂商协议按白名单逐步增加，而不是一次性承诺全兼容。

这样既保留最终方向，也避免把蓝牙认证、加密握手等超出硬件/时间预算的工作混入当前阶段。
